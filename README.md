# Tichori

A local prototype for demo identities and shared vaults. New vaults are Safe multisig contracts on **Base Sepolia, chain 84532**. Vault metadata and existing demo records persist in an encrypted Arkiv entity on **Rabdi, chain 7794095**, using `@arkiv-network/sdk` 1.0.1. SQLite is used only by the explicit, one-time migration command.

Identity matching, object scans, microphone listening and proximity remain simulations. Existing demo vaults and their requests remain simulated. New Safe vaults have real testnet contracts and signer-enforced thresholds; their transactions are handled in the Safe app, not by the demo approval flow. Anyone with access to this local app can switch demo identities. Use only testnet funds and synthetic identity information.

## Run locally

Requires Node.js 22.20+ and a persistent writable filesystem. Bind the demo to localhost; this API has no real authentication or per-user spending authorization and must not be exposed publicly.

1. Run `npm install`.
2. Copy `.env.example` to `.env` if you do not already have a local configuration. Configure `ARKIV_WALLET_PRIVATE_KEY`, the matching `ARKIV_WALLET_ADDRESS`, and your own `ARKIV_ACCESS_KEY` from [Arkiv Hub](https://hub.arkiv.network/access-keys). Fund the wallet with test GLM.
3. Generate an independent 32-byte encryption key and store its hex form as `ARKIV_STATE_ENCRYPTION_KEY`. Back up this key privately. Never commit or publish `.env`.
4. Choose a stable `ARKIV_NAMESPACE` and an explicit `ARKIV_MAX_TOTAL_FEE_TGLM`. Zero or missing budget disables writes. The journal conservatively reserves each signed transaction's maximum fee, including uncertain writes. Raising the setting increases the cumulative allowance; restarting does not reset it. Each namespace has its own journal and allowance. Do not change namespaces to bypass a budget.
5. Run `npm run arkiv:check` for read-only connectivity, signer, funding and state checks.
6. For existing SQLite data, stop the app and run `npm run arkiv:migrate` **before the first signup**. It encrypts existing records, verifies receipt and exact state readback, preserves IDs and invitations, and leaves `data/vault.sqlite` untouched. Migration refuses to overwrite existing Arkiv state. Invalid legacy relations or duplicate codes fail validation for explicit repair.
7. Run `npm run dev -- --hostname 127.0.0.1` and open http://localhost:3000.

Without a legacy database, the first valid signup creates the Arkiv entity. Signup generates a new EVM private key and public address in the browser. Choose a unique passphrase of at least 12 characters and back it up privately: the browser derives an AES-256-GCM key using PBKDF2-SHA256 (600,000 iterations and a random salt), encrypts the private key, and sends only the encrypted envelope and public address to the server. The passphrase and plaintext identity key are never sent to the API. The envelope is additionally protected by the server-side Arkiv aggregate encryption. The address is shown on the vaults page. Login is read-only and checks the passphrase locally against the encrypted key. The server still does not authenticate or authorize requests; the object description is a simulation, and access to the local API permits switching demo identities. Use a strong passphrase: anyone with the encrypted envelope can attempt offline guesses. If the passphrase is lost, the key cannot be recovered. The browser currently has no key export or signing integration: the generated identity address is separate from the connected wallet used for Safe deployment and the Safe app. For a new Safe vault, select Create vault, add the other signer wallet addresses, connect a creator wallet on Base Sepolia with test ETH, and approve deployment in that wallet. The connected creator is included; the threshold is a strict majority. The server verifies the mined Safe factory transaction, initialization, creation event, owners and threshold before storing its address in Arkiv. The vault page reads its ETH balance and current signer configuration from Base Sepolia and lets you copy the verified address. Use Safe for on-chain transaction signing and execution. The Listen button opens the Safe transaction queue; it does not use audio.

Deployment progress is kept in browser local storage. If deployment succeeded but saving to Arkiv failed, use Resume deployment. If the wallet submission outcome is unknown, enter the existing transaction hash from the wallet; the app will verify it rather than deploy again. Preserve browser data until registration succeeds. If the wallet transaction reverted, reconcile it before attempting a new deployment.

Existing demo vaults retain their old behavior and have no fund-holding address. Their transactions and balances remain simulations. Stored versions 1 and 2 are explicitly migrated to version 3 when read; a subsequent authorized write persists the upgraded representation. Legacy identifiers that are not EVM addresses remain preserved as legacy identifiers, without an invented address. Existing records have no generated key or passphrase, so they cannot log in through the new flow; their vault records and relationships are retained. There is no automatic identity reassignment or migration UI. Writes wait for a successful receipt and matching fresh Arkiv query before returning success. Group codes, object descriptions and encrypted private-key envelopes are omitted from the general API state. Login returns the requested identity’s encrypted envelope for browser-side unlocking; it is not access-controlled.

## Storage design and limits

`lib/vault.ts` preserves the demo rules and validates relationships. `lib/arkiv/store.ts` stores a named `tichori_state_v1` entity with an indexed namespace, revision, encoding and unindexed ciphertext bytes. Reads require the configured creator and owner. One encrypted aggregate makes each logical change atomic and avoids partially updated membership or approvals. It deliberately targets a small demo: serialized plaintext is capped at 100,000 bytes and exact writes must also fit the gas limits. This is not a scalable relational database replacement.

AES-256-GCM uses an independent server key, a fresh 12-byte IV, and authenticated context binding chain genesis, signer, namespace and format version. Public metadata still reveals the server wallet, namespace, revision, ciphertext length, timing and expiration. Encryption does not add real user authentication. Keep the signing wallet exclusive to this app and do not transfer the state entity.

The entity, including encrypted identity keys, expires after **30 days** at creation. A passphrase alone cannot restore an expired or lost encrypted key. The current prototype has no identity-key backup or export. Patching does not renew expiration. Renewal, archival and restore are not automated; arrange authorized Lifetime Extension before expiration if you need longer retention. Missing, expired, transferred, duplicate, corrupted or reset state produces an error rather than an automatic empty vault. Keep encryption keys and a backup of the original SQLite source safe. Do not delete the Arkiv journal to reset the demo or its spending allowance.

`data/arkiv-<signer>-<namespace>.json` stores verified entity metadata, reserved fees and any pending signed transaction for recovery; it is not the application database. Writes fsync signed intent/hash before broadcast and preserve confirmed receipts before readback. A shared signer lock coordinates processes on one host. All processes must share `VAULT_DATA_DIR`; distributed/serverless writers and use of this wallet by other apps are unsupported.

No write is automatically resent. The next request reconciles a pending hash, verifies the mined transaction and ciphertext, and resumes without another signature. If a receipt is unavailable or reverted, writes stop for operator investigation. After a crash, confirm the process is stopped and inspect the journal before removing a stale `.lock` file. Preserve the journal and its signed bytes; never print or upload it. Idempotency keys retain the last 100 successful mutation IDs in encrypted state. Repeating a key with changed input fails. The UI reuses a pending operation ID when retrying the same input, including after a reload; it clears that ID on success. A pending signup also retains its encrypted envelope in session storage so a retry does not generate a different identity; retry with the original name, object and passphrase. Closing the browser tab before an uncertain signup is reconciled loses this retry record. Changing the input starts a new operation.

The Arkiv MCP supplied network/schema/SDK guidance. Application reads and local signing use the SDK directly; credentials are never sent to the MCP.

## Checks

Run `npm run build` before `npm test`, then `npm run lint`. The test suite uses a local RPC fixture and a throwaway signer, encryption key and journal directory. It exercises the real SDK encoding, signed transactions, API flow, receipt recovery and error guards without spending testnet funds. Fixture results do not establish live Rabdi persistence; `arkiv:check` and an authorized migration/write with readback establish that separately. `npm run arkiv:verify` performs a paid storage update of the same vault contents with a fresh encrypted envelope and verifies the receipt and exact readback.
