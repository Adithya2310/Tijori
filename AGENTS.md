# Tijori contributor guide

## Product and current scope
Tijori is a local Next.js prototype for address-based demo identities and group transaction approvals. Object identities use scanner v2: a username linked to a personal object. The browser computes DINOv2 descriptors of the isolated object, and the server matches each login photo against the enrolled object before releasing key material. It distinguishes different objects but is not authentication or secure recovery: identical objects match, and anyone holding a stored profile can unlock the key. Legacy demo transfers remain simulations. Group acoustic matching uses real ggwave WASM and opt-in browser microphone access; it is a cooperative demo, not proof of physical proximity or identity. Active challenges can be replayed or relayed. Acoustic Send starts a check only and never creates, signs or authorizes a transfer. New vaults deploy Safe multisig contracts on Base Sepolia through an explicitly connected user wallet; on-chain transfers and signatures are handled by the Safe app. Vault metadata is verified and stored through the encrypted Arkiv Rabdi adapter. Never describe a mock as a security guarantee. Do not use real funds or sensitive information.

## Explicit local acoustic testing mode
`TIJORI_STORAGE_MODE=local` (legacy name `TICHORI_STORAGE_MODE` still works) explicitly selects `sdk/packages/server/src/storage/local-file.ts` through `sdk/packages/server/src/storage/index.ts` and needs no Arkiv credentials. `npm run dev:phone` serves the laptop and phones on HTTPS. Store the shared v5 state only in `data/local-demo/state.json`, encrypted with its private `encryption.key`, using the exclusive file lock and atomic durable writes. Never fall back to local mode automatically on Arkiv failures. Do not touch Arkiv journals, keys or budgets when running locally. Missing/corrupt initialized local state must fail closed. Local records are not automatically uploaded/migrated when switching to Arkiv. Original photos/masks stay in device memory. Compact versioned references and encrypted key envelopes are sent to the selected encrypted server store; older full references remain in IndexedDB/optional backups. Enrolled peers and groups refresh automatically for the two-device acoustic test. Local mode disables Safe registration. Real audio matching remains a replayable/relayable demo, not proof of physical proximity. SQLite remains a read-only migration source.

## Get started
Use Node.js 22.20 or later, then `npm install`. Configure server-only Arkiv credentials, an independent state encryption key and explicit cumulative fee allowance using `.env.example`. Follow README.md, run `npm run arkiv:check`, and run `npm run arkiv:migrate` before first signup to import an existing SQLite demo. Start with `npm run dev -- --hostname 127.0.0.1` and open http://localhost:3000. SQLite is only a read-only migration source. Do not delete Arkiv journals to reset state or spending limits. The server needs a writable persistent filesystem; this setup is not suitable for stateless/serverless deployment.

## Structure and contracts
- **The repository root is the Tijori app, a merchant of its own SDK.**
  - It installs `@tijori/server`, `@tijori/client` and `@tijori/react` from the npm registry. There are no workspaces and no source aliases, and app code must only import published entry points.
  - The integration is four pieces: `lib/tijori.ts`, `app/api/[...path]/route.ts`, `app/page.tsx` and the `@tijori/react/styles.css` import.
  - Root commands: `npm run dev`, `npm run build`, `npm test` (app tests: `tests/local-flow.mjs`, `tests/network.test.mjs`) and `npm run lint` (covers `sdk/` sources too). `arkiv:*` uses the published `tijori-server` CLI, and `dino:prepare` uses `tijori-client`.
- **`sdk/` is the npm SDK monorepo, with its own install and lockfile.**
  - Packages: `@tijori/core`, `@tijori/server`, `@tijori/client`, `@tijori/react` and `@tijori/invoices` in `sdk/packages`, versioned together with Changesets (`cd sdk && npx changeset`).
  - Commands in `sdk/`:
    - `npm run build` (`tsc -b` plus `scripts/postbuild-packages.mjs`)
    - `npm run typecheck`
    - `npm test`: unit tests plus the Arkiv flow, run against the local source on `tests/support/serve.mjs`
    - `npm run test:whitechain` (anvil)
    - `npm run release`
  - The root wrappers are `npm run sdk:build`, `npm run sdk:test` and `npm run sdk:test:whitechain`.
  - Changes reach the app only through a release. `npm run sdk:try-local` installs local tarballs into the app; `npm ci` goes back to the registry.
  - `sdk/examples/dao-site` is a separate integrator example.
  - Keep `@tijori/core` and the client's browser code free of `node:*` imports.
  - Never rename the identifiers in `@tijori/core/legacy`.
  - The integration guide is `docs/SDK.md`.
- `app/page.tsx`: the app is `<TijoriProvider><TijoriApp/></TijoriProvider>` from `@tijori/react` (object sign-up/login, dashboard, Whitechain vaults, treasury and acoustic checks) plus app-only slots in `app/legacy.tsx` (passphrase login, Base Sepolia Safes, simulated legacy approvals) and `PhoneAccess`.
- `sdk/packages/react/src/components/ProximityCheck.tsx`: two-minute acoustic broadcast/listen dialog, non-overlapping read-only polling, local expiry clock and audio cleanup.
- `sdk/packages/server/src/handler.ts` (`/api/proximity` and `/api/v1/proximity`) and `sdk/packages/core/src/proximity.ts`: declared membership, session start/status/verify/cancel, unique challenges, idempotent starts/matches/stops. All mutations use the shared Arkiv lock and encrypted aggregate; polling never writes. Storage failures return 503.
- `scripts/dev-phone.mjs`, `app/components/PhoneAccess.tsx` and `/api/network-info`: opt-in HTTPS LAN testing and QR links. Phone launchers use isolated Next build directories and the same Arkiv namespace/journal. Certificates remain local/ignored; users handle browser certificate warnings.
- `sdk/packages/core/src/identity-key.ts`: browser-side EVM identity generation, passphrase encryption and unlocking. Never send plaintext identity private keys or passphrases to the server.
- `sdk/packages/react/src/styles.css`: shared visual system and responsive layouts (`tj-` classes in `@layer tijori`, element rules scoped to `.tj-root`). `app/globals.css` holds only page basics and app-only styles.
- `app/api/[...path]/route.ts` mounts `@tijori/server` (`lib/tijori.ts`, configured with `fromEnv()`); `sdk/packages/server/src/handler.ts` holds the mock HTTP API routing and validation. `GET /api/state` returns `{ wallets, groups, transactions, storageMode, peers }`; peers exposes only enrolled identities’ public id/name/address. POST actions are `signup`, `login`, `groups`, `transactions`, `approve`, and `register-safe`; `GET /api/balance` reads a registered Safe’s current Base Sepolia ETH balance and signers; successful writes return the same state. Validation errors return `{ error }` with status 400; storage failures return status 503. Mutation idempotency keys retain the last 100 successful operations.
- `sdk/packages/server/src/services/service.ts` and `sdk/packages/core/src/api/domain.ts`: shared orchestration, provider hooks and server-calculated workflow presentation. `/api/v1/*` is the versioned integration scaffold; legacy routes use the same service. `sdk/packages/client/src/api.ts` (`createTijoriClient` from `@tijori/client`) is the frontend HTTP client; the browser object pipeline, acoustic modem (vendored ggwave), identity storage and `tijori-client prepare-assets` CLI also live in `sdk/packages/client`. See `docs/API.md` for payloads and teammate handoff.
- `sdk/packages/core/src/whitechain/`, `sdk/packages/server/src/whitechain/` and `sdk/packages/server/src/services/treasury.ts`: Whitechain treasury.
  - Contents: chain constants, EIP-712 SafeTx/attestation helpers, the pure treasury domain (proposals, invoices, CSV), derived inbox keys, and the server-only relayer.
  - Relayer rules: it holds one key, fsyncs its journal before every broadcast, simulates first, never resends uncertain transactions, and calls only the Safe factory and `TichoriPresenceGuard`.
  - Approval sessions: each approval checks the object, presence and the approver's own EIP-712 signature. Quorum counts only within one session.
  - Endpoints are listed in `docs/API.md`, under "Whitechain treasury endpoints".
- `contracts/`: Foundry project for `TichoriPresenceGuard` (Safe 1.4.1 guard requiring a co-presence attestation) and `TichoriSafeSetup` (installs guard + verifier at Safe creation). Tests etch the canonical Safe bytecode from `contracts/test/fixtures`. Run `forge test --root contracts`; `npm run sdk:test:whitechain` runs the local SDK server end-to-end on anvil (chain 1874).
- `sdk/packages/invoices` (`@tijori/invoices`) and `sdk/examples/vendor-studio`: vendor SDK and a separate vendor app for the invoice inbox.
- `sdk/packages/core/src/integrations.ts` and `sdk/packages/server/src/providers.ts`: replaceable server provider contracts and the current demo implementations. Real external-vault verification fails with 501 until configured. These hooks do not add authentication, application isolation or on-chain enforcement.
- `sdk/packages/server/src/storage/index.ts`: storage selector (`createTijoriServer({ storage })` or the `TIJORI_STORAGE_MODE` setting; `memoryStorage()` for tests); Arkiv by default, local encrypted file storage only with explicit opt-in. `sdk/packages/server/src/storage/arkiv.ts` handles SDK queries, encrypted aggregate writes, exclusive signer lock, fee reservation, signed transaction journal and recovery. `sdk/packages/core/src/vault.ts` validates domain state and relational integrity. `sdk/packages/server/src/cli.ts` (`tijori-server arkiv …`) handles read-only checks and explicit SQLite migration.
- `data/`: generated local state, never commit it.

New object sign-ups use scanner v2.
- **Enrollment:** a username plus a one-tap scan of about 3 angles. On-device SlimSAM isolates the object in the guide circle: the largest candidate lying entirely inside it, or the user's brushing (positive and negative point prompts) when they choose "Brush over it". DINOv2 produces the CLS token plus a foreground-only patch mean for each view, stored as a ~1 KB int8 view in an `objectProfile` v2 (1–5 views).
- **Login:** username plus one photo. The server's `dino-object-v2` provider (`@tijori/core/object-match`) compares the photo's descriptor and, only on a match, returns the key envelope plus the profile that derives its wrapping password.
- **Throttling and listing:** wrong objects are throttled per identity, and `/v1/object-identities` lists usernames only.
- **Approvals:** treasury approvals send a fresh photo descriptor, checked the same way.
- **Wrapping password:** the key's wrapping password still derives from the profile (an insecure demo: the server operator, server data or a backup file can unlock it). Never call this secure recovery or a passkey.
- **Scanner v1 identities** (0.1.x, browser-only matching) are told to sign up again. Their usernames may be re-registered.
- **Unchanged:** passphrase identities keep their original login path. Photos and masks never leave the device. Never store plaintext keys, passphrases or photos.
- **Thresholds:** `OBJECT_MATCH_CLS_WEIGHT` and `OBJECT_MATCH_THRESHOLD` come from the object-lab calibration (`sdk/examples/object-lab`, `npm run calibrate` in `sdk/`). Re-calibrate before changing the pipeline.
- **Speed:**
  - DINOv2 runs 8-bit on the CPU on every device, so descriptors are the same everywhere.
  - SlimSAM runs 8-bit on the CPU by default. WebGPU (16-bit image encoder) is opt-in through `configureAssets({ accelerator: 'webgpu' })`, because some browsers reject ONNX Runtime's WebGPU shaders; it falls back to the CPU.
  - One long-lived worker keeps the models loaded, and `ObjectCapture` preloads them.
  - The app is cross-origin isolated (COOP `same-origin`, COEP `credentialless`) so WASM can use several threads.
  - Re-check scores across runtimes in the object lab (`?gpu` tries WebGPU) after changing model precision.

Legacy v1/v2 identifiers without a valid EVM address remain legacy records with their relationships intact; they do not gain fabricated addresses or encrypted keys. They cannot log in through the new signup/login flow and have no automatic reassignment. A group has a unique mock signal code and at least two members. Codes and object descriptions are omitted from state responses. New Safe addresses, signers and deployment transactions are public on Base Sepolia. Wallet/namespace/revision/size/timing metadata remains public. The state entity expires 30 days after creation; patches do not renew it. Renewal requires separately authorized Lifetime Extension. The sender's approval is recorded when creating a legacy simulated transaction; a strict majority completes it. Object matching uses DINOv2 but remains an insecure browser check; acoustic matching uses real browser audio. Matches never change Safe thresholds or demo transaction approvals. Use different enrolled identities on separate devices; invite generated identity addresses for acoustic groups. Safe signer addresses and generated identity addresses are separate; checks use stored group membership, not live on-chain signer authorization. Legacy balances are placeholders. Safe vault balances and signer configuration are read from Base Sepolia; Safe transactions are managed in the Safe app.

The encrypted aggregate is version 7. The explicit additive v4 -> v5 migration (object profiles), the v5 -> v6 migration (empty Whitechain proposals and invoices) and the v6 -> v7 migration (scanner v2 object profiles) preserve every existing record. v5 allows new wallet records to carry a versioned compact objectProfile (~17 KB). No photos, masks, plaintext keys or user passphrases are stored. New object identities use prompted SlimSAM foreground isolation before DINOv2 on both enrollment/login; templates use 32 pooled q8 patch descriptors, so scores differ from full VILA and remain uncalibrated. /api/object-identities retrieves profiles/envelopes through the selected storage adapter; normal state omits them. The object-only API deliberately exposes wrapping material and is not authentication or secure custody. Passkey protection was offered and declined. Arkiv is authoritative for new profiles; browser storage is a cache/pending record. Legacy records are not automatically rekeyed or enrolled. Explicit v1/v2 address migration and additive v3 -> v4 migration preserve identities, Safe metadata, relationships and operation IDs, adding an empty proximity session history. A subsequent authorized mutation persists v6; polling does not spend gas. SQLite migration also preserves optional proximity tables. Sessions/matches retain history within the existing 100,000-byte cap; no automatic history deletion or entity renewal occurs. DINOv2 is integrated through Transformers.js in a browser worker with on-device page fallback; the pinned model and matching WASM runtime are served from the app’s own origin after checksum-verified preparation with `npm run dino:prepare`; new compact references are stored through Arkiv inside the aggregate cap; older full references remain in browser IndexedDB/optional backups. No original photos or plaintext keys are stored. Browser-only legacy references are origin-scoped and need an optional backup on a new origin; new compact references can be retrieved from the selected server store. Pending keys are saved before signup to allow safe retries. See README.md for the exact threat model and limitations.

## Suggested independent workstreams
1. **Identity and object verification:** replace mock identity creation/sign-in with a reviewed object-verification and key-management design. VILA (https://github.com/marcociama/VILA) supplies the adapted matching algorithm; its Python backend is not a runtime dependency. Its README describes DINOv2 features and encrypted vault/key derivation; object recognition alone is not a private key or proof of secure recovery. Define enrollment, authentication, recovery, threat model and consent before connecting it.
2. **Proximity and multisig:** harden the integrated acoustic protocol before connecting it to transaction signing or execution. Frequency matching alone does not prove proximity; consider replay, relay, spoofing, consent and quorum enforcement. Enforce authorization and quorum in a trusted contract, not only in the UI or this mock API.
3. **Platform integrations:** consider Anon RPC behind an explicit adapter; evolve the Arkiv aggregate only with an explicit schema migration. Define identity mapping, schemas, data retention and network behavior before migrating the local storage or claiming privacy properties.

Coordinate API/schema changes across workstreams. Store browser-encrypted demo identity key envelopes and validated compact reference profiles only inside the server-encrypted aggregate; never store plaintext private keys, passphrases, object images, or real personal data. Do not use real funds. Use migrations for future schema changes rather than relying on `CREATE TABLE IF NOT EXISTS`. Keep changes focused and commit them separately. Run `npm run build` and the relevant checks before handing off.
