# Tichori contributor guide

## Product and current scope
Tichori is a local Next.js prototype for address-based demo identities and group transaction approvals. Object matching uses a browser-side DINOv2 experiment; its check is bypassable and is not authentication or secure recovery. Legacy demo transfers remain simulations. Group acoustic matching uses real ggwave WASM and opt-in browser microphone access; it is a cooperative demo, not proof of physical proximity or identity. Active challenges can be replayed or relayed. Acoustic Send starts a check only and never creates, signs or authorizes a transfer. New vaults deploy Safe multisig contracts on Base Sepolia through an explicitly connected user wallet; on-chain transfers and signatures are handled by the Safe app. Vault metadata is verified and stored through the encrypted Arkiv Rabdi adapter. Never describe a mock as a security guarantee. Do not use real funds or sensitive information.

## Explicit local acoustic testing mode
`TICHORI_STORAGE_MODE=local` explicitly selects `lib/local-store.ts` through `lib/db.ts` and needs no Arkiv credentials. `npm run dev:phone` serves the laptop and phones on HTTPS. Store the shared v5 state only in `data/local-demo/state.json`, encrypted with its private `encryption.key`, using the exclusive file lock and atomic durable writes. Never fall back to local mode automatically on Arkiv failures. Do not touch Arkiv journals, keys or budgets when running locally. Missing/corrupt initialized local state must fail closed. Local records are not automatically uploaded/migrated when switching to Arkiv. Original photos/masks stay in device memory. Compact versioned references and encrypted key envelopes are sent to the selected encrypted server store; older full references remain in IndexedDB/optional backups. Enrolled peers and groups refresh automatically for the two-device acoustic test. Local mode disables Safe registration. Real audio matching remains a replayable/relayable demo, not proof of physical proximity. SQLite remains a read-only migration source.

## Get started
Use Node.js 22.20 or later, then `npm install`. Configure server-only Arkiv credentials, an independent state encryption key and explicit cumulative fee allowance using `.env.example`. Follow README.md, run `npm run arkiv:check`, and run `npm run arkiv:migrate` before first signup to import an existing SQLite demo. Start with `npm run dev -- --hostname 127.0.0.1` and open http://localhost:3000. SQLite is only a read-only migration source. Do not delete Arkiv journals to reset state or spending limits. The server needs a writable persistent filesystem; this setup is not suitable for stateless/serverless deployment.

## Structure and contracts
- `app/page.tsx`: client sign-up/login, dashboard, Safe deployment, legacy demo approvals and separate acoustic group creation/checks.
- `app/components/ProximityCheck.tsx`: two-minute acoustic broadcast/listen dialog, non-overlapping read-only polling, local expiry clock and audio cleanup.
- `app/api/proximity/route.ts` and `lib/proximity.ts`: declared membership, session start/status/verify/cancel, unique challenges, idempotent starts/matches/stops. All mutations use the shared Arkiv lock and encrypted aggregate; polling never writes. Storage failures return 503.
- `scripts/dev-phone.mjs`, `app/components/PhoneAccess.tsx` and `/api/network-info`: opt-in HTTPS LAN testing and QR links. Phone launchers use isolated Next build directories and the same Arkiv namespace/journal. Certificates remain local/ignored; users handle browser certificate warnings.
- `lib/identity-key.ts`: browser-side EVM identity generation, passphrase encryption and unlocking. Never send plaintext identity private keys or passphrases to the server.
- `app/globals.css`: shared visual system and responsive layouts.
- `app/api/[...path]/route.ts`: mock HTTP API and validation. `GET /api/state` returns `{ wallets, groups, transactions, storageMode, peers }`; peers exposes only enrolled identities’ public id/name/address. POST actions are `signup`, `login`, `groups`, `transactions`, `approve`, and `register-safe`; `GET /api/balance` reads a registered Safe’s current Base Sepolia ETH balance and signers; successful writes return the same state. Validation errors return `{ error }` with status 400; storage failures return status 503. Mutation idempotency keys retain the last 100 successful operations.
- `lib/db.ts`: server-only storage selector; Arkiv by default, local encrypted file storage only with explicit opt-in. `lib/arkiv/store.ts` handles SDK queries, encrypted aggregate writes, exclusive signer lock, fee reservation, signed transaction journal and recovery. `lib/vault.ts` validates domain state and relational integrity. `scripts/arkiv.ts` handles read-only checks and explicit SQLite migration.
- `data/`: generated local state, never commit it.

New signup uses an explicitly insecure object-only demo: real DINOv2 matching runs on-device, while a browser IndexedDB record (and optional recovery JSON) contains enrolled features and a random identity’s encrypted envelope; normal signup/login automatically remembers and loads this reference without requiring a file. A feature-derived internal password wraps the key; the file contains all wrapping material, so a file holder can decrypt the key without a photo. Never claim this is secure recovery or a WebAuthn passkey. Original images/masks never reach Arkiv. New compact versioned reference templates are stored inside the server-encrypted Arkiv aggregate. Existing passphrase identities retain their original login path. Each new signup generates an EVM key in the browser. The public address maps the identity; the private key is encrypted in the browser using AES-256-GCM and PBKDF2-SHA256 (600,000 iterations, random salt) with the internal feature-derived password for the object demo (or the user’s passphrase for existing passphrase identities), then stored inside the separately encrypted Arkiv aggregate. Login returns the encrypted envelope and checks the recovery-file-derived password or legacy passphrase locally. The unauthenticated local API and bypassable browser object check do not prevent impersonation or unauthorized API actions. The encrypted envelope is available to local API callers and susceptible to offline passphrase guessing. Never store plaintext identity keys or passphrases in API requests, logs, browser storage, or server state. The Arkiv writer private key remains independently held in server-only configuration. The object-demo recovery file is an insecure encrypted-key export; passphrase identities have no export/backup UI and neither flow has signing integration; the generated identity is separate from the connected Safe wallet. Lost passphrases or expired/lost Arkiv entities make the identity key unrecoverable.

Legacy v1/v2 identifiers without a valid EVM address remain legacy records with their relationships intact; they do not gain fabricated addresses or encrypted keys. They cannot log in through the new signup/login flow and have no automatic reassignment. A group has a unique mock signal code and at least two members. Codes and object descriptions are omitted from state responses. New Safe addresses, signers and deployment transactions are public on Base Sepolia. Wallet/namespace/revision/size/timing metadata remains public. The state entity expires 30 days after creation; patches do not renew it. Renewal requires separately authorized Lifetime Extension. The sender's approval is recorded when creating a legacy simulated transaction; a strict majority completes it. Object matching uses DINOv2 but remains an insecure browser check; acoustic matching uses real browser audio. Matches never change Safe thresholds or demo transaction approvals. Use different enrolled identities on separate devices; invite generated identity addresses for acoustic groups. Safe signer addresses and generated identity addresses are separate; checks use stored group membership, not live on-chain signer authorization. Legacy balances are placeholders. Safe vault balances and signer configuration are read from Base Sepolia; Safe transactions are managed in the Safe app.

The encrypted aggregate is version 5. The explicit additive v4 -> v5 migration preserves every existing record and allows new wallet records to carry a versioned compact objectProfile (~17 KB). No photos, masks, plaintext keys or user passphrases are stored. New object identities use prompted SlimSAM foreground isolation before DINOv2 on both enrollment/login; templates use 32 pooled q8 patch descriptors, so scores differ from full VILA and remain uncalibrated. /api/object-identities retrieves profiles/envelopes through the selected storage adapter; normal state omits them. The object-only API deliberately exposes wrapping material and is not authentication or secure custody. Passkey protection was offered and declined. Arkiv is authoritative for new profiles; browser storage is a cache/pending record. Legacy records are not automatically rekeyed or enrolled. Explicit v1/v2 address migration and additive v3 -> v4 migration preserve identities, Safe metadata, relationships and operation IDs, adding an empty proximity session history. A subsequent authorized mutation persists v5; polling does not spend gas. SQLite migration also preserves optional proximity tables. Sessions/matches retain history within the existing 100,000-byte cap; no automatic history deletion or entity renewal occurs. DINOv2 is integrated through Transformers.js in a browser worker with on-device page fallback; the pinned model and matching WASM runtime are served from the app’s own origin after checksum-verified preparation with `npm run dino:prepare`; new compact references are stored through Arkiv inside the aggregate cap; older full references remain in browser IndexedDB/optional backups. No original photos or plaintext keys are stored. Browser-only legacy references are origin-scoped and need an optional backup on a new origin; new compact references can be retrieved from the selected server store. Pending keys are saved before signup to allow safe retries. See README.md for the exact threat model and limitations.

## Suggested independent workstreams
1. **Identity and object verification:** replace mock identity creation/sign-in with a reviewed object-verification and key-management design. VILA (https://github.com/marcociama/VILA) supplies the adapted matching algorithm; its Python backend is not a runtime dependency. Its README describes DINOv2 features and encrypted vault/key derivation; object recognition alone is not a private key or proof of secure recovery. Define enrollment, authentication, recovery, threat model and consent before connecting it.
2. **Proximity and multisig:** harden the integrated acoustic protocol before connecting it to transaction signing or execution. Frequency matching alone does not prove proximity; consider replay, relay, spoofing, consent and quorum enforcement. Enforce authorization and quorum in a trusted contract, not only in the UI or this mock API.
3. **Platform integrations:** consider Anon RPC behind an explicit adapter; evolve the Arkiv aggregate only with an explicit schema migration. Define identity mapping, schemas, data retention and network behavior before migrating the local storage or claiming privacy properties.

Coordinate API/schema changes across workstreams. Store browser-encrypted demo identity key envelopes and validated compact reference profiles only inside the server-encrypted aggregate; never store plaintext private keys, passphrases, object images, or real personal data. Do not use real funds. Use migrations for future schema changes rather than relying on `CREATE TABLE IF NOT EXISTS`. Keep changes focused and commit them separately. Run `npm run build` and the relevant checks before handing off.
